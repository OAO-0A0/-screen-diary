# 屏幕日记

一个跑在你自己电脑上的记录工具：白天默默记下你切过哪些窗口、屏幕长什么样，
你有空时它一次性读完，写一篇当天的日记 —— 带软件时长分配、计划完成情况，
和一段**语气会跟着完成率变**的总结。

全程本地模型，不联网、不花钱、图不出机器，而且**当天就删**。

---

## 关于这一份（无数据版）

这是**可以直接用的最小版本**，只含运行必需的文件：

```
activity.py    前台窗口与键鼠空闲监测
analysis.py    时长统计、计划对比
charts.py      画图
collector.py   后台采集
config.py      配置定义
config.json    你的配置（当前是空计划）
diary.py       完整分析流程
journal.py     界面主程序（入口）
screenshots.py 截图与缩放
store.py       数据存取
vision.py      本地视觉模型调用
weekly.py      周报
启动.bat        双击启动
```

**不含**的东西（那些是开发用的，不影响使用）：

* 回归测试（原项目里有 224 个用例）
* 演示数据生成脚本
* 我的开发笔记与方案文档
* 任何已生成的数据和日记

**第一次运行会自己建 `data/` 和 `diary/`**，所以你下载下来直接双击就行。
另外这一份的 README 是原项目的完整文档，里面「文件说明」那节会提到上面
列出的那些开发文件 —— 那些在你这份里没有，忽略即可。

### 需要额外装的东西

只有一样：**Ollama**（本地模型运行环境），以及两个模型：

```bash
ollama pull gemma3:4b          # 视觉模型，读截图用
ollama pull qwen3:4b           # 文本模型，写总结用
```

两者加起来约 **5.4 GB** 磁盘、跑起来占 **约 3.8 GB 显存**（分析时）。

> Ollama 装好后确认服务在跑（默认 `127.0.0.1:11434`）。
> 模型名可以改 `config.py` 里的 `VISION_MODEL` / `TEXT_MODEL`。
> **换视觉模型前先确认它支持 vision**：`ollama show <名字>` 看
> `capabilities` 里有没有 `vision` —— 有些小模型（比如 `gemma3:1b`）
> 只有 `completion`，读不了图。

Python 方面**不需要 `pip install` 任何东西** —— 只用标准库 + PIL
（画图用）+ Windows 自带能力。PIL 装不上也能跑，只是没有那两张图。

### 跑不起来的话

按顺序查这三项：

1. `ollama list` —— 两个模型在不在
2. 浏览器打开 `http://127.0.0.1:11434` —— 服务在不在（应该返回一行字）
3. 界面上按「我有空，开始分析」，看下方日志说什么 —— 失败原因都写在那里

界面里有个「设置 → 补分析没生成的日子…」，能列出所有记过事的日子，
用来手动补分析或重跑某一天。

## 快速开始

**双击 `启动.bat`**。

程序一开就自动开始采集（默认模式），你不用管它。要做的只有两件事：

1. **设个今日计划**（点界面上的「设置计划」）
2. **离开电脑前**按一下「我有空，开始分析」

## 按钮

主界面上只留常用的动作，其余收进**设置**菜单：

| 按钮 | 干什么 |
|---|---|
| **开始记录** | 开一段手动记录，会问你这段时间打算干什么（可留空） |
| **结束并统计** | 关掉这段，立刻弹出时长和软件分配 |
| **我有空，开始分析** | 批量读图 → 算时长 → 对计划 → 写日记。期间再按一次可中止 |
| **看今天的日记** | 直接打开今天那篇 |
| **本周周报** | 生成 / 重算本周周报（平时只在周日自动生成） |
| **专注模式** | 看网课 / 思考难题时打开，见下 |
| **设置 ▾** | 菜单：浏览日记 / 设置计划 / 补分析 / 打开文件夹 |

> 一开始主界面上并排摆了五六个按钮，越加越难一眼找到主要动作。
> 现在「偶尔用一次」的都收进设置菜单了。

手动模式和默认模式是**叠加**的，不冲突：默认模式一直在记，手动模式是在这条长河里切一段出来重点看。

### 专注模式（看网课 / 思考时用）

**解决的问题**：默认离开阈值是 10 分钟没碰键鼠就算你不在电脑前。
但看网课、思考一道难题时，你几十分钟不碰键鼠，**人就在电脑前**。
实测过：看 40 分钟网课会被记成 **1 分钟的活跃** —— 那段时间既不算活跃
也不算离开，直接悬空。

打开专注模式后，离开阈值拉长到 **2 小时**，那段时间**一律算活跃**。

| | 离开阈值 | 中途起身 30 分钟 |
|---|---|---|
| 普通 | 10 分钟 | 扣掉，算离开 |
| 专注 | 2 小时 | **照算活跃**（按约定不判离开）|

代价是这段时间里你真走了也会算在用 —— 所以它是**手动开关**，状态一眼看得见
（标题下面那行），而且**两小时后自动关掉**（和离开阈值同一个值），
免得你忘了关、后面真走开的时间全被算成活跃。倒计时也显示在那行上。

状态存在 `config.json` 的 `focus_mode`，下次启动会恢复。

**实现上的一个要点**：专注期间产生的事件都带 `focus: True` 标记，
统计端把落在专注时段里的「离开区间」丢掉。不这么做的话，专注期间的一次
小停顿仍会被记成离开、被扣掉，和「一律算活跃」的约定不符。

### 补分析

**设置 → 补分析没生成的日子…**，列出所有记过事的日子让你勾选：

```
☑ 2026-09-28  周一   未生成   20 条事件    0 张截图
☑ 2026-09-29  周二   已生成    9 条事件    0 张截图
☐ 2026-10-01  周四   已生成   38 条事件   12 张截图

已选 2 天 · 0 张截图 · 预计约 12 秒
其中 1 天已有日记，会被重新生成（旧日记另存为 diary.old.md）
```

- **每行都显示事件数和截图数** —— 有没有截图直接决定那天日记的质量
  （有图 → 有屏幕印象；没图 → 只有时长），不显示的话你没法理解
  为什么某天的日记特别干瘪。
- **已生成的日子默认不勾**，免得手快覆盖掉。
- 批量跑，逐天进度，中途可中止；**单天失败会跳过继续**，不整批停掉。
- 重跑前把旧日记存成 `diary.old.md`（只留最近一次）—— 你可能往总结后面
  手工补过话，重跑会覆盖，留一份还能捞回来。
- 整批跑完**统一释放显存一次**（批量期间保持加载，省掉每天一次的加载等待）。
- 跑完如果涉及的周已有周报，会问一句要不要重算。

### 浏览窗口

日记在磁盘上是 `diary/年-月/年-W周/日期/` 三层目录，一周就有 23 个文件 ——
想看前几天的，光靠「看今天的日记」不够。浏览窗口按同样的三级结构列出
日报和周报，选中时右侧显示那天的活跃时长、计划完成情况和同目录的文件：

```
2026-10  [8 项]
  2026-W40  (09-28 ~ 10-04)
    10-04  周日  [8小时56分  2/2]     ← 今天的话标绿
    10-03  周六  [8小时26分  1/1]
    ...
    周报 2026-W40  [合计 70小时1分  计划 9/10  7/7 天]
```

**树的结构和文件夹一一对应**，所以界面上看到的位置就是它在磁盘上的位置，
不会让人对不上号。摘要数字直接读 `summary-<day>.json`，不重算 ——
翻个列表就把 30 天的事件流全读一遍太浪费。

## 它是怎么省资源的

核心设计：**白天一次都不调用模型**。

| 阶段 | 干了什么 | 开销 |
|---|---|---|
| 白天采集 | 每 3 秒看一眼前台窗口；换了应用并稳定 5 秒才截一张图 | **59 ms/张，CPU 约 0.1%** |
| 你按分析 | 批量读图、写日记 | 每张约 1.1 秒，占 3.8 GB 显存 |

实测数据：

* 截图：JPEG 291 KB / 26 ms（存 PNG 是 655 KB，BMP 是 9 MB，一天能攒 12.7 GB）
* 视觉模型：**896 宽只要 1.1 秒，原尺寸 2048 宽要 17 秒还看错** —— 所以缩放是必须的
* 采集器常驻内存约 28 MB

## 挂着不管会怎样

**不会自动分析。** 你不点「我有空，开始分析」，它就永远只采集不分析 ——
没有任何定时器或日期判断会替你触发。

但程序按「常驻几周」来设计，所以这几种情况都处理了：

### 跨过午夜会自动分账

采集循环会定期比对日期，变了就切换记录文件和截图目录：

```
23:58  你在用 VS Code     -> data/events-2026-10-03.jsonl
00:03  你还在用 VS Code   -> data/events-2026-10-04.jsonl
```

切换前会把待定的窗口先落盘到旧那天，并在新一天写一条 `rollover` 标记
（否则新一天第一个事件会被当成「你从那一刻才开始用电脑」）。
同一天只会切一次（有幂等保护）。

### 启动时会提醒没分析的日子

如果某天有记录但没生成日记，开程序时会问你：

```
2026-10-03 有记录，但还没生成日记。
要现在补分析吗？
```

多个日子会一次列出来，补分析的是最近那天。**因为常驻程序很容易忘了点分析
就关机**，不提醒的话那天的记录就一直躺在 `data/` 里，你看不见也分析不了。

### 截图会自动清理

启动时删掉超过 **7 天**的截图目录（`config.json` 的 `keep_shots_days` 可调）。

留 7 天而不是当天就删，是给「忘了分析」留补分析的机会 —— 一周之内你随时
可以补分析某天，补完后周报也能跟着重算。分析成功后当天的图会立刻删除，
所以正常使用下磁盘占用是 0。

> 超过 7 天还没分析的日子会单独提示一次，说明截图已被清理，
> 之后只能靠窗口标题统计（没有屏幕内容了）。

### 一直不切窗口也能记到

有个场景值得单独说，因为它踩过坑：

```
打开屏幕日记之前就已经在看文献
之后几小时一直没切过窗口
直到关闭程序
```

早期版本**这种情况一条都记不到** —— 事件只在「窗口切换」时产生，
而那个窗口从程序启动起就没变过，统计出来是 0 秒。

现在靠三件事解决：

| 机制 | 作用 |
|---|---|
| 启动时把当前窗口记成**待定窗口** | 之后你切窗口、或退出程序时，它就会落盘 |
| 关闭程序前**收尾落盘** | 保证「从切过去到关程序」这段不丢 |
| 每 2 分钟一条**键鼠心跳** | 证明「这个时刻你还在用电脑」，给统计提供活动证据 |

心跳一天几百条、几 KB，可以忽略。

它顺带修掉另一个更隐蔽的问题：旧版把单个窗口的时长上限设成 **90 分钟**，
**连续看 2 小时文献会被砍成 1.5 小时**。那个上限本意是防「忘了关的窗口刷时长」，
但这类问题已经由「排除自己 + 键鼠空闲检测」解决了，所以现在放宽到 4 小时，
只作为病态数据（比如系统时间被改）的保险。

## 截图什么时候拍

不按固定间隔，而是**窗口切换 + 稳定 5 秒**才拍。但要区分两件事：

* **窗口事件**：每次标题变化都记（标题里有信息，比如你在哪个目录）
* **截图**：只在**换了应用**时才拍（按「进程 + 窗口类」判断）

为什么分开：在文件资源管理器里翻目录，进程和窗口类完全没变，只有标题里的
路径在变。只按标题判断的话，实测每 6 秒切一个目录、翻 15 个目录会**拍 14 张**，
而这 14 张对「你在干什么」几乎没有新增信息。现在同样翻 15 个目录只拍 **1 张**。

| 场景 | 截图数 |
|---|---|
| 翻 15 个目录（同一个资源管理器窗口） | **1 张** |
| 浏览器换 5 个标签页 | **1 张** |
| 真正切换 6 个不同应用 | **6 张** |
| 离开电脑再回来 | 回来第一张**必拍** |

效果上大致是：看视频两小时不动 → 0 张；正常工作一天 → **几十张**，
而不是几百张（如果同应用内反复切换的话）。

`Alt+Tab` 快速划一圈不会触发连拍（有 5 秒静置要求）。

> 想调回「每次标题变化都拍」：把 `collector.py` 里
> `should_shoot = (app_key != self._last_shot_app)` 改成 `should_shoot = True`。

## 时长是怎么算的

按**事件之间的时间差**累加，不是数截图：

```
09:15:00  VS Code
09:43:00  Edge        -> VS Code 记 +28 分钟
10:05:00  VS Code     -> Edge 记 +22 分钟
```

两个容易搞混的概念，代码里分开了：

* **窗口停留久** —— 你盯着同一个窗口 40 分钟，那是真在用，照实算（上限 90 分钟，防忘关的窗口刷时长）
* **真的离开** —— 靠键鼠空闲（`GetLastInputInfo`）判断，不是靠「事件间隔大」猜。否则你专心写代码一小时会被当成离开

### 「回到桌面只剩日记软件」这个问题怎么解的

原来的实现有个漏洞：你关掉所有窗口回到桌面，前台就是日记软件本身，
然后你走开 —— 那个窗口会被无限累加，日记里写成「你在用 Python」，时长还是假的。

三层处理：

1. **程序自己永远不记录。** `python.exe` / `pythonw.exe` 在忽略名单里。
2. **窗口事件先「待定」不落盘。** 只有确认你还醒着（又切了窗口）才写。
   真走了的话，这条就只到「离开起点」为止。
3. **离开单独计时。** 键鼠空闲跨过 10 分钟就判定离开，离开起点取
   「空闲推算的时刻」和「最后窗口起点」里更早的那个，把缝隙也算进去。
   离开期间切窗口一律不记、不截图。

实测（09:00 用 VS Code → 10:30 切到日记软件 → 走开 → 12:30 回来）：

| | 修复前 | 修复后 |
|---|---|---|
| 日记软件时长 | 无限累加 | **0 秒** |
| VS Code 第一段 | 一直算到集合结束 | **87 分钟**（截断在离开起点） |
| 离开时长 | 未识别 | **123 分钟** |
| 总结里的描述 | 「你在用 Python」 | 只有真实的软件 |

## 系统自带应用是怎么认出来的

Windows 上有几个坑，光看进程名会错得很离谱：

| 现象 | 原因 |
|---|---|
| 打开「设置」→ 进程名是 `applicationframehost.exe` | **所有 UWP 应用共用这个宿主进程**（设置、计算器、照片、应用商店…），进程名区分不出是哪个 |
| 打开文件夹 → 进程名是 `explorer.exe` | 同一个进程既是桌面外壳，也是文件资源管理器窗口 |
| 「设置」窗口**没有标题** | 想靠标题认都不行 |

早期的实现是「按进程名排除」，所以 `explorer.exe`、`systemsettings.exe`、
`applicationframehost.exe` 全被一刀砍掉 —— 结果文件管理器和设置**全都识别不出来**。

现在改成**按窗口类 + 有没有标题**判断：

| 判断依据 | 处理 |
|---|---|
| 窗口类 `Progman` / `WorkerW` | 忽略 —— 桌面本身 |
| 窗口类 `Shell_TrayWnd` 或 `XamlExplorer_*` | 忽略 —— 任务栏、开始菜单 |
| 标题为空 | 忽略 —— 隐藏窗口、壳窗口 |
| 窗口类 `CabinetWClass` / `ExploreWClass` | **记录** —— 文件资源管理器窗口 |
| 窗口类 `ApplicationFrameWindow` | **记录** —— UWP 应用，用标题当名字 |
| 窗口类 `Windows.UI.Core.CoreWindow` | 按进程名判断 —— 系统提示（音量、输入法）忽略，「设置」记录 |
| 其它有标题的窗口 | 记录 |

实测结果（真实打开文件夹验证过）：

```
explorer.exe            CabinetWClass               -> 文件资源管理器
systemsettings.exe      Windows.UI.Core.CoreWindow  -> 设置
applicationframehost.exe ApplicationFrameWindow      -> 计算器
explorer.exe            ApplicationFrameWindow（空标题）-> 忽略
nahimic3.exe            Windows.UI.Core.CoreWindow  -> 忽略
```

显示名会尽量友好：标题命中映射表就用人话（「设置」「计算器」「照片」），
没命中就直接拿标题当名字。

## 计划与总结

计划写在 `config.json` 里，也能在界面上改：

```json
"plan": [
  {"start": "09:00", "end": "11:00", "task": "写代码"},
  {"start": "14:00", "end": "16:00", "task": "看论文"}
]
```

**完成情况要你手打勾**，不让模型猜。原因很实在：在 VS Code 待了 90 分钟
不等于写了 90 分钟代码，模型推断这个只会给你一个看着确定、其实瞎猜的数字。

不过「相关软件实际时长」会算出来给你参考 —— 按**计划时段和窗口事件的时间重叠**算，
不是按软件名匹配（按名字匹配会把你看论文时顺手开的 Chrome 重复算进两个任务）。

### 总结的语气分档

档位由完成率算出来，模型只负责用这个语气写。**不让模型自己判断好坏** ——
它经常过分宽容，什么都说「你今天已经很棒了」。

| 完成率 | 语气 |
|---|---|
| ≥ 120% | 得瑟 |
| 80–120% | 满意 |
| 50–80% | 阴阳怪气 |
| 20–50% | 阴阳怪气加强 |
| < 20% | 破防自嘲 |

## 产出

目录按**月 / 周 / 天**三级组织，一周用 ISO 周号（周一是第一天），**每天单独一个文件夹**：

```
diary/2026-10/2026-W41/
├── 2026-10-05/                ← 一天一个文件夹
│   ├── diary.md               当天日记正文
│   ├── chart.png              当天软件分配
│   └── timeline.png           当天时间线
├── 2026-10-06/
├── 2026-10-07/
├── ...
├── weekly-2026-W41.md         周报（放在周目录，和天文件夹平级）
└── weekly-chart-2026-W41.png  周图
```

**为什么一天一个文件夹**：一天产出 1 篇正文 + 2 张图，一周就是 21 个文件。
分开之后「一天的东西」自成一体 —— 删一天、打包一天、整体搬走都不会牵连别的天。

文件名用固定的 `diary` / `chart` / `timeline`，不带日期：日期已经由两级
文件夹表达了，文件名再带一遍是重复，改名或复制时还容易和内容不一致。

**为什么用 ISO 周号而不是 W1/W2**：它跨年不会乱（2026-12-28 属于 2026-W53，
而 2029-12-31 属于 2030-W01），而且天然可排序。

**跨月的那一周不会分家**：周号只决定组内分组，月份取**天数占多数**的那个月。
比如 2029-12-31(一) ~ 2030-01-06(日)：1 月占 6 天，所以整周（含周一和
周报）都进 `2030-01/2030-W01/`。早期版本按各天自己的月份放，同一个周文件夹
被拆成两半。

旧的日记结构会在启动时自动迁移过来（含图片），冲突时旧文件存成 `diary.old.md`。

### 每日日记（约 65 行）

- 软件分配（前 5 项 + 「其它 N 项」）
- 计划 vs 实际对照
- 那段语气随完成率变的总结
- 当天分配图
- **屏幕印象**（折叠）：每张截图一句话描述，点开才看

屏幕印象是「那天你到底在屏幕上看什么」的**唯一记录** —— 截图分析完就删了，
过后再也补不出来。所以它折叠着但必须留着。

它确实常认错（实测把微信认成「客户关系管理软件」、把知乎认成 Notion），
所以不该默认铺开，但更不该丢。**周报里刻意没有这一段**：一周几十张图的
描述堆起来没人看。

### 周报（约 38 行）

- **一张图**：7 根横条 = 7 天，每根按软件分色，一眼看出哪天忙、忙在什么
- 每日概览表：日期 / 星期 / 活跃 / 主要软件 / 计划完成
- 本周软件分配（前 8 项）
- 计划完成合计
- 一段总结（语气档位按**整周**完成率定，沿用日报那套）

**什么时候生成**：当天的日报分析完，如果那天是**周日**，就顺手把这一周的
周报一起做了。绑在这里而不是单独定时，是因为周日分析完这一周的数据才刚齐。

### 计划快照：周报怎么还原历史

计划只存在于 `config.json` 这一个全局文件里，它记的永远是「当前」的计划。
周日生成周报时再去读它，拿到的是你最后改过的那一份 —— 实测出过
「这天没有记录，却显示计划 1/1」这种矛盾。

所以每天分析时会把**当时的计划落一份快照**进 `summary-<day>.json`。
补分析旧日子时，如果已有快照就以**已有的**为准，不会被后一次分析冲掉。

> 全都按「没有计划」算。光隔离 `data/` 不够，配置也必须一起隔离。

### 关于脚本文件命名

`启动.bat` 是纯 ASCII 的，**它调用的 Python 脚本也用 ASCII 名字**，这是刻意的：

bat 里必须保持纯 ASCII，**包括它调用的文件名**。实测在 bat 里写中文文件名，
那行会被 cmd.exe 按 936 解析成乱码碎片，然后当作命令执行
（报 `'Screen' is not recognized as an internal or external command`）。
所以凡是被 bat 调用的脚本，文件名只能用 ASCII。

> ⚠️ 编码约束，改坏了会直接出问题：
> * `启动.bat` 必须保持**纯 ASCII**。cmd.exe 用控制台代码页(936)解析批处理文件，
>   文件里有中文会碎成乱码**并被当成命令执行**，启动直接失败。
>   所有中文输出都交给 Python 打印，它自己管编码。

### 关掉程序再打开

**程序关闭期间没有任何东西在记录**，所以统计端会以为那片空白是「你在用」。
实测过：用 30 分钟 → 关掉 → 隔 2 小时 → 再打开用 30 分钟，
算出 **3 小时 2 分**（真实 1 小时），静默多出那 2 小时。

现在做了两件事：

| 时机 | 做什么 |
|---|---|
| **启动时** | 如果上次事件到现在有空档（≥10 分钟），补一条**离开事件**覆盖它 |
| **从离开回来时** | 显式把当前窗口记一条（带 `awake` 标记）当离开区间的终点 |

第二件是必须的：窗口事件只在**签名变化**时产生，你离开期间用的还是同一个
窗口，回来时签名没变，`tick()` 不会产生任何事件 —— 那样回来的那段会整段
消失（实测丢过 30 分钟）。

修好之后同一个场景算出 **1 小时 1 分**（多出的 1 分钟是末段余量）。

> 跨天的空档不管：昨晚 23:50 关掉、今早 9:00 打开，中间的夜不属于今天，
> 由跨天分账负责。

## 数据格式

事件流是**按天一个 JSONL 文件**，不用数据库：

* 追加写，程序崩了也不丢已写的部分
* 出问题你直接用记事本就能看、能改
* 一年几十万行也就几 MB

**按年月分目录存**（一天三个文件，一年 1100 个，堆在一个目录里太乱）：

```
data/
├── 2026-09/
│   ├── events-2026-09-28.jsonl    每行一条：窗口切换 / 空闲 / 心跳
│   ├── sessions-2026-09-28.json   手动记录的段
│   ├── summary-2026-09-28.json    分析结果（含屏幕印象）
│   └── archive-2026-09.zip        月度归档包
├── 2026-10/
└── shots/2026-09-28/*.jpg         截图（分析后删除）
```

升级前存在根目录下的旧文件**仍能读到**（读取会自动退回旧位置），
启动时也会自动搬进新结构。

### 月度归档

**每月 7 号之后**（7 号起每天启动时都检查一次），把上一个月的数据目录
打包成 `archive-<月>.zip`。

- 为什么定在 **7 号**而不是 1 号：你可能会在月初补分析上个月最后几天
  （截图保留 7 天，所以月初补得上）。留这个缓冲更稳。
- **不删原目录**，只多出一个压缩包。一年才 1.4 MB，删掉省的这点空间
  远不如「随时能打开看原始记录」值钱。
- 归档是**幂等**的，打过包就跳过。如果你一个月没开程序，之后启动会把
  漏掉的历史月份都补上。

## 排错

| 现象 | 处理 |
|---|---|
| 分析报「视觉模型不可用」 | 确认 `gemma3:4b` 在：`ollama list`；没有就 `ollama pull gemma3:4b` |
| 显存不够 | 分析前先把游戏关掉；视觉模型要 3.8 GB |
| 时长明显偏少 | 你中途离开过，空闲时段被算成「离开」了（这是故意的） |
| 离开时间没被识别 | 键鼠空闲要连续超过 10 分钟才算离开。短暂走开不算 |
| 日记软件出现在记录里 | 不该发生。若出现，检查 `activity.py` 的 `NOISE_PROCESSES` 里有没有 `python.exe` / `pythonw.exe` |
| 桌面本身被记成活动 | 检查 `activity.py` 的 `SHELL_CLASSES`，`progman` / `workerw` 应在里面 |
| 某个系统应用还是认不出 | 先在界面上切到那个窗口，再看 `data/events-*.jsonl` 里记下的 `cls` 字段（窗口类），按上面的表加进 `SHELL_CLASSES` 或 `UW_APP_PROCESSES` |
| 显示成 `applicationframehost` | 说明标题没命中 `config.py` 的 `UWP_TITLE_NAMES`，把标题加进去即可 |
| 截图一大堆 | 正常，分析完会删。想立刻清：删 `data/shots/` 下的目录 |
| 数据文件找不到 | 现在按年月放在 `data/2026-09/` 里；升级前的旧文件仍能读到，启动时自动搬过去 |
| 归档包什么时候建 | 每月 7 号之后的首次启动。想立刻建：删掉 `archive-*.zip` 再启动一次 |
| 专注模式自己关了 | 设计如此：开启两小时后自动关，避免忘了关导致时长虚高 |
| 认不出屏幕内容 | 视觉模型会看错（实测把微信聊天认成「写作软件」）。软件时长是准的，文字描述当参考 |
| 计划里没有的任务也算时长 | 只有时段重叠且有软件匹配才算，其它不计入 |
| 关闭界面后还在记录 | 退出时会自动收尾并停止采集；确认托盘里没有残留进程 |
| 昨天的活动记到了今天 | 不该发生（跨天已自动分账）。若出现，跑 `python tests_跨天.py` 看是否回归 |
| 提醒了不想补分析的日子 | 直接选「否」，那天会留到超过 7 天后不再提示 |
| 想留更久的截图 | 改 `config.json` 的 `keep_shots_days`（默认 7） |
| 周报没生成 | 只有**周日**那天的日报分析完才会生成周报。补分析周日那天即可 |
| 周报里的计划不对 | 计划快照存在 `summary-<day>.json` 的 `plan`/`plan_done` 里，检查那两天的文件 |
| 老日记找不到 | 旧结构（`年-月/日期.md` 或 `年-月/年-W周/日期.md`）启动时会自动迁到 `年-月/年-W周/日期/diary.md`，图片一起搬；冲突的旧文件存成 `diary.old.md` |
| 想跑测试又不弄脏数据 | 测试已自动隔离，不用管；手工实验可设 `SCREENJOURNAL_DATA` 指到临时目录 |
| 七天日报的计划都一样 | 说明分析时 `config.json` 里的计划没按天变。日报读的是**当前**计划，所以要「设当天的计划 → 分析当天」 |
| 演示数据里混进了真实活动 | 演示周不能包含「今天」。选完全过去的一周，否则启动界面时采集器会把真实桌面写进去（实测混进过一条 23:05 的真实事件） |
| 没开过程序的日子也有个数据文件 | 不该发生。心跳只在键鼠刚动过（`idle == 0`）时写，启动后就走开不会留下文件 |

## 两个已知局限

1. **窗口标题和屏幕内容可能不一致。** 实测遇到过一次：标题写「百度一下」，
   截图里却是 B 站（标签页标题没同步）。所以程序**两者都记** —— 标题用来算时长，
   截图用来看内容。

2. **视觉模型会认错。** 它把微信聊天界面认成过「在线写作软件」。日记里的文字描述
   是**它的印象**，不是事实；软件时长那部分是准的。
